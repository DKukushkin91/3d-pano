# Add Feature

Запрос: `$ARGUMENTS`

## Phase 1: Understand

- Запусти `/learn`, если область незнакома.
- Найди возможность в `openspec/roadmap.md` и `openspec/parity.md`: к какому этапу она относится, какие
  требования уже описаны, что из этого использует neometria.
- Проверь живые спецификации (`pnpm exec openspec list --specs`) — не описано ли уже поведение.

## Phase 2: Clarify (по одному вопросу)

Узкие вопросы по одному, лучше с вариантами. Темы (очевидное пропускай):

- **Публичный API** — имена, форма опций, события. Любое новое имя — вопрос пользователю.
- **Границы** — что входит в изменение и что нет.
- **Совместимость** — ломает ли существующие контракты.
- **Безопасность** — новые сетевые запросы, HTML из данных, CSP.
- **Проверка** — какой контракт-тест или сценарий песочницы докажет требование.

## Phase 3: Approaches

2–3 варианта с компромиссами, рекомендуемый — первым:

```
**Вариант A: [название]** (рекомендую)
- как работает: …
- плюсы: …
- минусы: …
```

## Phase 4: Propose

После выбора направления — `/opsx:propose`. Все решения из диалога записываются в `design.md` в раздел
«Решения» со статусом «согласовано»; всё, что пришлось додумать, — со статусом «ждёт согласования».

## Phase 5: Approve

Покажи пользователю `proposal.md`, требования и список решений «ждёт согласования». Реализация не
начинается, пока такие решения остаются.

## Phase 6: Implement

`/opsx:apply` по `tasks.md`. После каждого логического шага — `pnpm check` и `/commit`. В конце —
документация для интеграторов (`README.md`, `docs/`), затем `/opsx:archive`.

## Principles

- Один вопрос за раз.
- Всегда 2–3 подхода до фиксации решения.
- Рекомендация по умолчанию, но решает пользователь.
- YAGNI: урезать объём, а не раздувать.
