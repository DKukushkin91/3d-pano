# Design

## Context

M1 (`add-core-viewer`, в архиве) держит в просмотрщике одну сессию сцены. Сессия — это загрузчик плюс
слои превью и основного источника в видеопамяти. Каждый кадр рисуется прямо в canvas: на слой один
полноэкранный проход фрагментного шейдера. `create-pano-viewer.ts` уже занимает 282 строки из 300
разрешённых. Сцены, переходы и кэш в него не помещаются, работу со сценами нужно вынести.

Мотивация и объём описаны в [proposal.md](./proposal.md), поведение — в дельтах `specs/`. Ограничения
задают [конституция](../../constitution.md):

- чистая комната;
- ноль зависимостей ядра;
- до 300 строк на файл и SonarJS;
- бережность к памяти: принцип VI.2.

## Goals / Non-Goals

**Goals:**

- Логика смены сцен проверяется контракт-тестами в Node без WebGL. Навигатор получает фабрику сессий
  и часы извне, поэтому тесты подставляют поддельные.
- Композитинг кадра через framebuffer, на котором без переделки строятся переходы M5–M6 (iris, slide,
  zoom, шаг в 3D) и докачка тайлов M4.
- Вне перехода кадр стоит столько же, сколько в M1: framebuffer используется только во время
  смешивания.

**Non-Goals:**

- Приоритеты и отмена отдельных запросов (M4). Здесь очередь предзагрузки работает на уровне сцен.
- Восстановление после потери WebGL-контекста (M7).

### Жизнь смены сцены

```
showScene(id) ──► проверка опций (RangeError синхронно)
              ──► неизвестный id → отклонение unknown-scene, ничего не меняется
              ──► та же сцена на экране → true (D51)
              ──► перебить прошлую смену (её промис → false)
              ──► snapshot { sceneId: id, status: loading, isTransitioning: true }, sceneChange, sceneLoadStart
              ──► сессия из кэша или новая (без превью, D53); пока грузится — старая на экране
              ──► готово основное изображение → sceneReady
                    cut:   новая сцена на экране, вид и ограничения новой (D50), конец
                    blend: старая в framebuffer A (живая при keep, иначе замершая),
                           новая в framebuffer B с камерой; вес = easing(t / durationMs)
              ──► конец смешивания: framebuffer освобождены, isTransitioning: false, промис → true
```

Навигатор — одна машина состояний с тремя состояниями: `idle` (одна сцена), `loading` (старая на
экране, новая грузится), `blending`. У каждой смены свой токен. Ответ устаревшей смены сравнивается с
текущим токеном и отбрасывается — так «последний вызов побеждает» без отмены промисов.

### Кадр с композитингом

Вне смешивания кадр рисуется как в M1: слои сцены прямо в canvas. Во время смешивания:

1. Старая сцена рисуется в текстуру A. При `keep` — с живой камерой каждый кадр. Иначе — с замершей
   камерой один раз и заново при смене размера буфера.
2. Новая сцена рисуется в текстуру B с живой камерой.
3. Проход смешивания: полноэкранный треугольник, `color = mix(texture(A), texture(B), weight)`.

`weight = clamp(easing(elapsedMs / durationMs), 0, 1)` считается только в TypeScript и передаётся
uniform-ом. Новых формул, живущих и в GLSL, и в TypeScript, нет: в шейдере только `mix`. Функции
плавности покрываются контракт-тестами по значениям в 0, 0.5 и 1 и по монотонности там, где она
положена.

## Risks / Trade-offs

- [Две текстуры размером с буфер во время смешивания: на 4K при `maxPixelRatio` 2 это около 2 × 33 МБ]
  → они живут только во время смешивания (D63) и не входят в `sceneCacheMegabytes`. Бюджет кэша
  описан в документации как память сцен, а не всего просмотрщика.
- [Кэш на 256 МБ держит одну 8K-эквиректангулярную сцену (~170 МБ с MIP) плюс немного] → для neometria
  с гранями по 2048 это 6 × 16 МБ × 4/3 ≈ 128 МБ на сцену, то есть две сцены. Бюджет настраивается.
  В M4 тайлы уменьшат размер сцены.
- [Байты считаются по своим текстурам, а драйвер может выделять больше] → бюджет — это оценка, и в
  документации он назван оценкой.
- [Сравнение тура по JSON в React на каждом рендере] → тур — данные в десятки килобайт, а
  `JSON.stringify` занимает доли миллисекунды. Если станет заметно — сравнение по ссылке плюс
  документированный `useMemo`.
- [Предзагрузки по одной медленнее параллельных] → не мешают текущей сцене (D57). Приоритеты появятся в
  M4.
- [Старая сцена при `view` не `keep` замирает] → это выбор владельца (D42). Пользователь видит
  растворение неподвижной картинки, а управляет новой сценой.

## Migration Plan

- Для ядра изменение обратно совместимо: новые методы, опция, поле снимка и событие. Код M1
  компилируется без правок.
- React: смена пропа `tour` больше не пересоздаёт просмотрщик. Хостам, которые на это полагались
  (например, чтобы сбросить вид), нужно передать `key` компоненту. Это пишется в `docs/react.md`.
- neometria переедет после M3 (`add-hotspots`) и M4 (`add-multiresolution`).
