# Конституция проекта 3d-pano

Версия 1.0.0 · черновик 2026-10-01, ждёт согласования

Конституция — неизменяемые правила, которым подчиняется каждая спецификация, план, задача и строка кода.
Если спецификация противоречит конституции, правится спецификация. Конституция меняется только
отдельным изменением с повышением версии и записью в журнал внизу файла.

## I. Чистая комната и лицензия

3d-pano — наша собственная разработка под лицензией MIT. Мы делаем движок, который по возможностям не
уступает коммерческим просмотрщикам панорам, но не содержит ни строчки их кода.

1. **Никогда не открывать, не деобфусцировать, не дизассемблировать и не копировать** файлы сторонних
   проприетарных движков, их версий и плагинов. Такие файлы не хранятся в репозитории и не являются
   источником требований. Агенты и люди не читают их содержимое.
2. Источники требований разрешены только такие:
   - публично описанные возможности продуктов («умеет кубические панорамы», «есть переход blend») —
     идеи и возможности не защищены авторским правом, защищён код и текст;
   - код наших собственных приложений (neometria, agoi), которые сегодня используют чужой движок, — он
     показывает, какие возможности реально нужны;
   - общедоступная математика и стандарты (WebGL2, WebXR, Pointer Events, формулы проекций и easing).
3. Документацию сторонних продуктов не цитируем и не пересказываем близко к тексту. Описываем
   поведение своими словами и своими терминами.
4. Публичный API, имена опций и формат конфигурации — **свои**. Чужие имена в API не
   используются; соответствие старым понятиям при переезде описывает проект-потребитель, а не
   документация библиотеки.
5. Название пакета, классов и событий не содержит чужих товарных знаков.
6. Зависимости рантайма ядра — ноль. Всё, что попадает в опубликованный пакет или нужно ему в рантайме
   (peer-зависимости адаптеров), — только с лицензиями MIT, BSD, ISC или Apache-2.0. Инструменты
   разработки, которые не попадают в пакет (линтеры, служебные скрипты), могут быть и под LGPL —
   обязательства LGPL возникают при распространении, а мы их не распространяем.

## II. Независимость от фреймворка

1. Ядро (`@dkukushkin/3d-pano`) не импортирует ни один UI-фреймворк и работает с обычными DOM-элементами.
2. Адаптеры живут в отдельных точках входа (`/react`, далее `/element`, `/vue`) и являются тонкой
   обёрткой над публичным API ядра — без собственной логики панорамы.
3. Импорт любой точки входа безопасен на сервере: на уровне модуля нет обращений к `window`,
   `document`, `navigator`, WebGL. Всё, что касается браузера, начинается при создании просмотрщика.
4. Пакет — только ESM, `sideEffects: false`, крупные возможности (VR, гироскоп, видео) подключаются
   так, чтобы неиспользуемые выпадали при tree-shaking.

## III. Код читает человек

1. Один файл — одна ответственность и не больше 300 строк (считая пустые строки и комментарии) —
   проверяет линтер. Переусложнения (когнитивная сложность, глубокая вложенность, дубли) ловит
   SonarJS в составе `pnpm lint`.
2. Чистая математика (углы, векторы, проекции, ограничения вида, анимации, выбор тайлов, валидация
   конфигурации) отделена от побочных эффектов (DOM, WebGL, сеть) и не знает о них.
3. Имена говорят, что значат: `yaw`, `pitch`, `fieldOfView`, `tileLevel`, а не `h`, `v`, `f`, `l`.
   Однобуквенные имена запрещены линтером. Магические числа — именованные константы с единицами
   измерения в имени (`INERTIA_FRICTION_PER_SECOND`, `MAX_PIXEL_RATIO`).
4. Углы в публичном API — в градусах, внутри математики — в радианах; преобразование происходит
   в одном месте и явно (`toRadians`, `toDegrees`).
5. Шейдеры — читаемый GLSL ES 3.00 в отдельных `.ts`-модулях с именованными функциями, без
   минификации и генерации строк из кусочков, кроме явного выбора проекции.
6. Комментарии — только JSDoc на русском над экспортируемыми сущностями и объясняют «почему»,
   а не «что». Остальное должно читаться из кода. Проверяется скриптом `check:comments`.
7. Форматирование и линтинг — oxfmt и oxlint с проверкой типов; правила не отключаются точечно без
   объяснения в спецификации.

## IV. Безопасность по умолчанию

1. Конфигурация тура — это данные, а не код. Нет встроенного скриптового языка, `eval`,
   `new Function`, строковых обработчиков событий. Поведение задаётся только функциями JS/TS.
2. Текст из конфигурации выводится через `textContent`. HTML в DOM попадает только из элементов,
   которые создал сам хост-код.
3. Библиотека работает под строгим CSP: без `unsafe-eval`, без внедрения `<style>`/`<script>`.
4. Сеть — только загрузка ресурсов, явно указанных в конфигурации, через подменяемый загрузчик.
   Нет телеметрии, проверок лицензии, обращений к сторонним доменам.
5. URL ресурсов проверяются: разрешены `http(s):`, `blob:`, `data:image/*` и относительные пути.
   Прочие схемы (`javascript:` и т. п.) отклоняются с понятной ошибкой.
6. Ошибки загрузки и отсутствия WebGL2 не роняют страницу: просмотрщик сообщает о них событием
   `error` и остаётся в предсказуемом состоянии.

## V. Сначала спецификация (SDD на OpenSpec)

1. Каждая возможность — изменение OpenSpec: `proposal.md` (что и зачем) → дельты требований
   `specs/` → `design.md` (как, модули, решения) → `tasks.md` (упорядоченные задачи) → код →
   архив, который вливает дельты в живые спецификации `openspec/specs/`.
2. Изменение поведения начинается с изменения спецификации. Код без требования — лишний код.
3. Решения, которых нет в запросе владельца, спецификациях или коде, согласуются с владельцем до
   реализации. В `design.md` у каждого решения есть статус: «согласовано» или «ждёт согласования».
4. Каждое требование покрыто проверкой: контракт-тестом (`node --test` по собранному `dist`) для
   логики или сценарием в песочнице (`examples/playground`) для отрисовки. Имя теста содержит
   название требования.
5. Задача закрыта, когда `pnpm check` зелёный, а сценарии требования воспроизведены. Каждая
   законченная группа задач — отдельный коммит.

## VI. Производительность и бережность к устройству

1. Отрисовка только по необходимости: если вид, ресурсы и анимации не изменились, кадр не
   рисуется.
2. Память текстур ограничена бюджетом; тайлы вне поля зрения вытесняются по LRU, неактуальные
   загрузки отменяются.
3. Плотность пикселей ограничена (`maxPixelRatio`), чтобы не жечь батарею на экранах 3×.
4. В горячем цикле отрисовки не создаются временные объекты, если этого можно избежать без
   ущерба читаемости.

## VII. Доступность

1. Просмотрщик управляется с клавиатуры и имеет доступное имя.
2. DOM-хотспоты — настоящие фокусируемые элементы (`<button>` по умолчанию).
3. `prefers-reduced-motion` учитывается: автоповорот и анимированные переходы по умолчанию
   отключаются или сокращаются.
