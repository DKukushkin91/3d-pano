# 3d-pano — руководство для агентов

Этот файл — общий для всех ИИ-агентов (Claude Code, Codex, Cursor и других). `CLAUDE.md` подключает его
целиком и добавляет только специфику Claude Code.

## Что это

`@dkukushkin/3d-pano` — собственная библиотека для просмотра панорам и виртуальных туров на WebGL2:
кубические, эквиректангулярные и многоуровневые (тайловые) панорамы, хотспоты, переходы между сценами,
3D-туры и VR. Ядро не зависит от фреймворков, React — отдельная точка входа `@dkukushkin/3d-pano/react`.

Цель — паритет возможностей с коммерческими движками (прежде всего с тем, который сейчас стоит в
neometria) при собственном, читаемом и безопасном коде. Главный потребитель и источник требований —
`talent.frontends.neometria` (`src/widgets/panorama-tour/`).

## Четыре правила, которые важнее всего остального

1. **Советуйся, прежде чем придумывать.** Всё, что не следует напрямую из запроса пользователя,
   спецификаций OpenSpec, конституции или существующего кода — имена публичного API, форматы данных,
   структура модулей, новые зависимости, расширение объёма, «улучшения по пути» — сначала выносится
   пользователю вопросом: 2–3 варианта, рекомендуемый первым, с компромиссами. Мелкие решения внутри
   уже согласованного дизайна принимаются самостоятельно и записываются в `design.md` изменения.
2. **Чистая комната.** Никогда не открывай, не читай, не деобфусцируй и не цитируй код и файлы
   проприетарных движков, даже если такой файл оказался на диске.
   Требования берутся только из публичных описаний возможностей, кода наших приложений и стандартов.
   Подробно — [openspec/constitution.md](openspec/constitution.md), принцип I.
3. **Сначала спецификация.** Любое изменение поведения начинается с изменения OpenSpec
   (`/opsx:propose`), проходит согласование с пользователем и только потом реализуется (`/opsx:apply`).
   Код без требования — лишний код.
4. **Коммиты — Conventional Commits на русском.** `feat(core): добавить загрузку кубических панорам` —
   тип и область на английском, описание на русском в повелительном наклонении со строчной буквы, без
   точки. Тело объясняет «почему». Реализация режется на логические коммиты (один коммит — одна
   завершённая мысль, после которой `pnpm check` зелёный). Пока работаем в `main`; `push` — только по
   просьбе. Трейлеры `Co-authored-by`, `Generated with …` и подобные не добавляются.

## Команды

```bash
pnpm install          # pnpm 11 закреплён в packageManager
pnpm check            # всё сразу: формат, линт, комментарии, чистая комната, спецификации,
                      # типы, сборка, контракт-тесты, publint/attw, песочница
pnpm build            # tsdown → dist/
pnpm build:watch      # сборка в фоне для песочницы
pnpm dev              # песочница examples/playground (Vite)
pnpm test:unit        # node --test scripts/*.unit.mjs по собранному dist
pnpm lint             # oxlint --type-aware
pnpm format           # oxfmt
pnpm typecheck        # tsc --noEmit (TypeScript 7)
pnpm check:specs      # openspec validate --all --strict
pnpm check:docs       # TS/TSX-примеры из README.md и docs/ компилируются против dist
pnpm exec openspec list            # активные изменения
pnpm exec openspec list --specs    # живые спецификации
```

Тестов на jsdom, Vitest и снапшотов нет и не будет. Логика проверяется контракт-тестами `node --test`
против собранного `dist` (через служебную точку входа `internal`), отрисовка — сценариями в песочнице.

## SDD на OpenSpec

| Путь                                  | Что лежит                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `openspec/constitution.md`            | Неизменяемые принципы проекта. Читать перед любым артефактом.                             |
| `openspec/roadmap.md`                 | Зачем проект, термины, этапы M1…M5 и какие изменения их закрывают.                        |
| `openspec/parity.md`                  | Матрица возможностей против коммерческих движков и список того, что использует neometria. |
| `openspec/specs/<capability>/spec.md` | **Живые** спецификации — как библиотека ведёт себя сейчас.                                |
| `openspec/changes/<change>/`          | Изменения в работе: `proposal.md`, `design.md`, `tasks.md`, дельты `specs/`.              |
| `openspec/changes/archive/`           | Завершённые изменения.                                                                    |

Цикл:

1. `/opsx:explore` — разобраться, если задача неясна.
2. `/opsx:propose` — создать изменение. Требования пишутся как `### Requirement:` с SHALL/MUST и
   сценариями `#### Scenario:` (WHEN/THEN); текст на русском, ключевые слова OpenSpec — на английском.
3. **Согласование с пользователем.** Все придуманные решения вынесены в `design.md` в раздел
   «Решения» со статусом «согласовано» или «ждёт согласования». Реализация не начинается, пока
   остаются «ждёт согласования».
4. `/opsx:apply` — реализация по `tasks.md`, задача за задачей, с коммитом на каждый логический шаг.
5. `pnpm check` зелёный, сценарии из спецификации воспроизведены в песочнице.
6. `/opsx:archive` — дельты вливаются в живые спецификации.

## Архитектура

Актуальная архитектура описана в `design.md` действующего изменения и в живых спецификациях. Инварианты:

- `src/index.ts` — публичное ядро, `src/react.ts` — React-адаптер (`'use client'` только здесь),
  `src/internal.ts` — служебная точка входа только для контракт-тестов.
- Чистая математика (углы, векторы, проекции, ограничения вида, анимации, тайлы, валидация) лежит
  отдельно от побочных эффектов (DOM, WebGL, сеть) и не импортирует их.
- На уровне модулей нет обращений к `window`/`document`/`navigator`: импорт безопасен в Node и при SSR.
- Ядро без зависимостей рантайма.

## Стиль кода

Полные правила — [.claude/reference/RULES.md](.claude/reference/RULES.md). Коротко:

- Имена: `TFoo` (type), `IFoo` (interface), `EnumFoo` (словарь `as const` + тип `TFoo` из его значений;
  `enum` и `const enum` не используются), `useFoo` (хук), `handleFoo` (обработчик), `UPPER_SNAKE_CASE`
  (константы, с единицами в имени), `kebab-case` для файлов.
- Однобуквенные имена запрещены, кроме `x`, `y`, `z`, `w` в векторной математике.
- Файл — не больше 300 строк; когнитивная сложность функции — не выше 15, вложенность — не глубже 4
  (oxlint + SonarJS в `pnpm lint`).
- Комментарии — только JSDoc на русском над экспортом и только про «почему». Проверяет
  `pnpm check:comments`.
- Нет `any`, необоснованных `as`, `@ts-ignore`, отключений правил линтера. Сужение типов — через
  предикаты `isFoo(value): value is TFoo`.
- Ранний выход; `if` всегда со скобками и на отдельных строках; функция делает одно.
- Публичные углы — в градусах, внутренние — в радианах, преобразование явное.
- В горячем цикле отрисовки — без лишних аллокаций, но не ценой читаемости.

## Документация для интеграторов

`README.md` и `docs/*.md` — на английском (пакет публичный, как video-scrubber). Спецификации, JSDoc
и коммиты — на русском. Любое изменение публичного API обновляет `README.md`/`docs/` в том же коммите,
иначе изменение не считается законченным.

## Подводные камни

- Список чужих имён для `check:clean-room` лежит в локальном `scripts/clean-room.local.json` (вне git);
  без него проверка пропускается. Файлы проприетарных движков не читать и не коммитить.
- Сгенерированные OpenSpec файлы (`.claude/skills/openspec-*`, `.claude/commands/opsx/`, `.agents/`,
  `.cursor/`) руками не правим — их обновляет `pnpm exec openspec update`.
- `pnpm-workspace.yaml` содержит исключение `minimumReleaseAgeExclude` для OpenSpec: pnpm 11 по
  умолчанию не ставит пакеты моложе суток.
